# Record of design choices

- [2026-09-08] [context: SLN-31 navigate-traces skill] chose question-driven primary / level-ladder reference over level-by-level primary because the level tour risks becoming a compulsory ceremony and triggers osmosis on precise-question tasks. Rejected level-by-level primary because it displaces the agent's natural reading when it already has a precise run and question.
- [2026-09-08] [context: SLN-33 significant_runs UUID bug] chose to normalize types in both the source adapter (cast parent_run_id/dotted_order to str) AND the core filter (str() both sides of the membership check) because defense in depth is cheap and the core should not depend on upstream type discipline. Rejected core-only fix because it leaves the type drift in the canonical model; rejected source-only fix because it makes the core fragile to future adapters.
- [2026-08-18] [context: SmithDB SDK migration] chose to wrap async SDK calls with asyncio.run() inside the LangSmithSource adapter over propagating async through TraceSource + CLI because the CLI is fully synchronous, makes few network calls per invocation, and propagating async would touch 6 files and break the established sync pattern. Rejected full async propagation because it fragments the codebase for negligible performance gain.
- [2026-08-18] [context: SmithDB SDK migration] chose to keep read_run (legacy) for resolve_trace_id over migrating to runs.retrieve because runs.retrieve requires project_id as input, but resolve_trace_id's purpose is to discover the project_id from a bare run_id — a chicken-and-egg problem with no SmithDB API solution. Rejected runs.query(ids=[run_id]) because project_ids is now required even for ID-based queries. read_run works until removal on 31 Jan 2027; TODO documented in the method.
- [2026-08-18] [context: SmithDB SDK migration, resolve_trace_id refinement] chose to implement the SmithDB-native path NOW (runs.retrieve with configured project) with read_run as a deprecated fallback, rather than waiting until read_run is removed. The common case (run in configured project) uses the new API immediately; the edge case (cross-project) falls back to legacy with a deprecation warning. This gives months of runway to catch edge cases before the hard deadline. Rejected "wait and migrate later" because there's no benefit in waiting and we lose the opportunity to discover issues early. Rejected "brute-force search all projects" because it's slow, fragile, and fights the SmithDB project-scoped design.
- [2026-09-08] [context: SLN-17 task & outcome assessment] chose a thin-slice CLI command (`assess`) with manual input over automatic LLM-based scoring or LangSmith evaluation integration because the issue explicitly scopes this to manual input first (inference is L2). The assessment is stored as `assessment.json` alongside the sanitized trace, not embedded in the trace itself, because it is analyst metadata, not trace data. Rejected embedding in Trace.extra because it would couple assessment lifecycle to trace lifecycle and complicate round-tripping. Rejected a quality score because the issue says "not a quality score — a cited assessment." Surfaced in skeleton and info so the analyst sees outcome context before interpreting metrics.
- [2026-09-08] [context: SLN-21 focused diagnostic skill] chose to evolve the existing `analyze-agent` skill in place rather than creating a new `diagnose-trace` skill because SLN-21 says "an evolution, not a replacement" and the existing skill already had the principles, triangle, mechanisms reference, and benchmark. The evolution replaces the level-by-level step tour (Steps 1-6) with a question-driven workflow (name question → retrieve evidence → verify → write findings), replaces RunEO/TraceEO with the findings report format from SLN-21, and adds explicit stopping rules. Rejected a separate skill because two overlapping diagnostic skills would confuse the analyst about which to use. Rejected keeping the level-by-level tour as primary because it risks becoming a compulsory ceremony on precise-question tasks (same reasoning as SLN-31).
- [2026-09-09] [context: SLN-36 narrative range filter] chose `--from N --to M` plus `--around-step N` as flags on the existing `narrative` command over a new `narrative-range` command because the range is a scoping concern, not a new view. The narrative step numbering (1-based, counting all significant runs) is reused as the filter axis. Rejected `--head N` / `--tail N` because they don't support arbitrary ranges. Rejected semantic filtering ("show only error steps") because it's a different feature with different complexity.
- [2026-09-09] [context: SLN-37 context-at --outputs-only] chose a symmetric `--outputs-only` flag mirroring the existing `--inputs-only` over a new command because the asymmetry was the friction — the analyst could see inputs-only but not outputs-only. Rejected making `--inputs-only` the default because the current default (both) is the right behavior for first-time use.
- [2026-09-09] [context: SLN-38 tool-call extraction] chose `--tool-calls-only` as a flag on `run-detail` over a new `tool-calls` command because it's a bounded extraction of run-detail data, not a new analysis view. The flag works on LLM runs only and returns structured JSON with name/args/id per tool call. Rejected a new command because it would duplicate the run-lookup and error-recovery logic already in run-detail.
- [2026-09-09] [context: SLN-40 Windows Unicode] chose UTF-8 stdout reconfiguration at startup (`sys.stdout.reconfigure(encoding='utf-8')`) over per-print encoding guards or ASCII-only output because reconfiguration preserves content fidelity for trace-derived Unicode (which we don't control) while fixing the crash for authored Unicode. Rejected ASCII-only output because it loses information from trace content. Rejected per-print guards because they'd need to wrap every print call. Added a project rule to minimize special characters in authored text, but the robustness fix handles whatever still arrives.
- [2026-09-09] [context: SLN-41 coherence audit fixes] chose to honor `--format json` in `skill-check` and `prompt diff` over removing the flag because composability matters for agent consumers. For `skill-check`, JSON returns `{expected, observed, match, false_positive}`. For `prompt diff`, JSON returns `{has_differences, diff}` wrapping the unified diff text — structured enough for programmatic `has_differences` checks without overcomplicating the diff itself. Chose to enforce `--from/--to` pairing in `context-at` with exit code 2 (usage error) over silently falling through to single-step mode because the Recoverable contract requires a precise error when the agent's intent is clear but the flags are incomplete.
- [2026-09-09] [context: SLN-42 skeleton --errors-only] chose a `--errors-only` flag on `skeleton` over a new `skeleton-errors` command because error triage is a scoping concern on the existing view, not a new view. The flag filters to runs with `error` set or `status != "success"`, keeps the root summary line (trace-level status), and reports the filtered-out count. Rejected a new command because it would duplicate the skeleton's run-formatting and assessment-header logic. Complements `error-neighborhood` (which shows context around errors) — `--errors-only` is the "which steps failed?" question, `error-neighborhood` is the "what happened around the failure?" question.
- [2026-09-09] [context: SLN-43 run-detail --inputs-only/--outputs-only] chose to mirror `context-at`'s `--inputs-only`/`--outputs-only` flags on `run-detail` over a new command because the asymmetry was the friction — `context-at` could show inputs-only or outputs-only but `run-detail` could not, despite both being L3 drill-down commands. The flags omit the related-runs section when active (focused on one section). Rejected making `--tool-calls-only` mutually exclusive with these flags in the parser because argparse doesn't enforce mutual exclusion cleanly with `store_true`; the handler prioritizes `--tool-calls-only` if set (documented in the docstring).
- [2026-09-09] [context: mutual exclusion enforcement] chose to enforce mutual exclusion of scoping flags (`--tool-calls-only`/`--inputs-only`/`--outputs-only` on `run-detail`, `--inputs-only`/`--outputs-only` on `context-at`) in the CLI handler with exit code 2 (usage error) over argparse's `add_mutually_exclusive_group` because the handler approach gives a precise error message naming the conflicting flags, while argparse's default message is generic. Also applies to `context-at`'s `--inputs-only`/`--outputs-only` which were silently producing empty output before. Rejected silent prioritization (the previous behavior) because the Recoverable contract requires a precise error when the agent's intent is clear but the flags conflict.
- [2026-09-09] [context: SLN-39 target-timeline --compact] chose a `--compact` flag on `target-timeline` over a new command because compactness is a scoping concern on the existing view, not a new view. The flag omits args and result lines, keeping only tool name + status + run ID per touch. JSON mode omits the `args`/`result` keys and sets `compact: true`. Rejected changing the default to compact because the full args/result are needed for drill-down questions ("what did it pass to that tool?"). The compact mode is for the overview question ("did the agent keep touching the same target?"), the default is for the detail question.
- [2026-09-22] [context: cost-of-cognition in mechanism vocabulary] chose analyst-facing labels (`context.unsupplied_fact`, `tool.probabilistic_discovery`, `tool.prose_payload`, `context.redundant_derivation`) over a deterministic "CoC metric" because whether cognition was mechanically derivable requires domain semantics the canonical trace model lacks — a CLI score would emit fake precision and violate the deterministic/honest-metrics contract. Labels record the observable spend; the should-we-mechanize judgment stays in the finding's Assessment. Rejected a dedicated `mech.*`/`coc.*` prefix because the existing `domain.pattern` taxonomy already locates the pattern and `fault_locus` carries the repair target.
- [2026-09-22] [context: SoL-Pi paper arXiv:2609.20519 review] chose to adopt the 4 surviving harness mechanisms (`harness.action_fusion`, `harness.context_compact`, `harness.observation_pack`, `harness.evidence_reducer`) as candidate-improvement vocabulary over reframing the detector backlog (SLN-8/19/20) around them, because the mechanisms are solution-shaped and cost-vertex-only — detection must stay problem-shaped and cover quality/latency frictions their catalog doesn't address. Rejected treating their constants (e.g. 10KB payload threshold) as universal because they were selected on coding-agent harnesses.
- [2026-09-22] [context: interface for analyst agents] chose CLI-only with continued investment in agentic UX over adding an MCP server, because the evidence navigation contract already satisfies MCP-tool design properties (bounded, connected, recoverable, composable) and the interfaces are interchangeable — the effort goes to ergonomics, not a second transport. Rejected MCP exposure because it adds a transport layer without changing what the analyst can do.
- [2026-09-22] [context: SLN-25 minimal slice — findings persistence] chose `findings.json` alongside `assessment.json` with sequential IDs (f1, f2) and subcommands (`finding add|list|remove|clear`) mirroring `ati`/`prompt` over embedding findings in the trace or a single report file, because findings are plural, append-accumulating analyst metadata — same lifecycle as assessment. Chose free strings for `pattern`/`secondary_patterns`/`fault_locus` over argparse choices because the mechanisms.md vocabulary is explicitly living and must not be enforced at the storage boundary; kept fixed choices for `impact`/`strength`/`axis` because those axes are stable.
- [2026-09-22] [context: pre-push maintainability refactor] chose to split the four monoliths (`cli/main.py`, `domain/__init__.py`, `storage/__init__.py`, `representations/__init__.py`) into per-concern modules with `__init__.py` kept as a re-export facade, over one-module-per-function or leaving as-is. `cli/` splits by command family (discovery, views, metrics, records, prompts, ati, system) with each module owning its handlers + `register(sub)`; `storage/` splits into per-area mixins composed by `TraceStore`; `representations/` splits one file per view over `common` helpers; `domain/` splits model (`trace`) from analyst records (`records`). Rejected removing the facade re-exports because `from self_improve_cli.X import Y` is the documented public import shape used by tests, metrics, and skills — compatibility beats purity.
